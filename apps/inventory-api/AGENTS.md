# Inventory API Agents

`apps/inventory-api` is the Fastify backend that persists the **inventory** domain (items, recipes, vendors, purchase orders, counts, waste, activity). It owns its own Postgres database via `packages/db-inventory` (`INVENTORY_DATABASE_URL`) and is the single write path for floor + backoffice inventory actions.

It is a sibling of `apps/kds-api`, deliberately serving **both** Floor (`apps/crew-web`) and Backoffice (`apps/backoffice-web`) so neither calls the other (Iron Law 4). It never touches the KDS or analytics databases (Iron Laws 1 + 5).

Use these checks when relevant:

- `pnpm --filter @rop/inventory-api build`
- `pnpm --filter @rop/inventory-api test`
- `pnpm --filter @rop/inventory-api test:integration`  # real ephemeral Postgres via Testcontainers (Docker); see [docs/TESTING.md](../../docs/TESTING.md)
- `pnpm --filter @rop/inventory-api lint`
- `pnpm --filter @rop/inventory-api dev` # http://localhost:4100

## Routes

- `GET  /api/inventory` — full `InventoryDataset` (re-validated against the contract before it leaves the API). The **activity** feed is capped to the most-recent `DATASET_ACTIVITY_LIMIT` (200) rows so the hot read stays flat as it grows (GH #184; the only consumer slices it to 5, and the contract field is `z.array(...)`, so the bound is server-only). `counts` and `waste` are **deliberately read in full** — the backoffice computes whole-history aggregates + an "all recorded events" CSV over them, so a row cap would corrupt totals; bounding those needs a date window + a paginated `?since=` history endpoint (the issue's deferred needs-ADR portion), along with ETag/304.
- `GET  /api/recipes/plate-costs` — `PlateCostsResponse`; plate cost per Clover menu item for analytics-api's `dim_item_cost` ingest ([ADR-0031](../../docs/decisions/0031-profitability-analytics-cost-dimension.md)). Brand-level (`InventoryItem.costCents`) so not location-scoped; read-only like `/api/inventory`.
- `GET  /api/actual-cogs-inputs` — `ActualCogsInputsResponse`; count-based actual COGS per between-count window (beginning + received − ending, valued at current item cost) for analytics-api's `dim_actual_cogs` ingest / yield-variance lens ([ADR-0031](../../docs/decisions/0031-profitability-analytics-cost-dimension.md)). Read-only like `/api/recipes/plate-costs`; stamped with the configured Clover merchant id.
- `GET  /api/inventory/pos/:id` — `InventoryPurchaseOrderDetail` (PO + per-line `line_items`, each now carrying the agreed `unit_cost_cents`) for the floor receive flow and the backoffice edit drawer.
- `POST /api/inventory/pos` — body `InventoryPurchaseOrderCreate`; create a `submitted` PO (catalog D3). Per-line `unit_cost_cents` is persisted (feeds the order total + the edit-drawer prefill).
- `PUT  /api/inventory/pos/:id` — body `InventoryPurchaseOrderUpdate`; edit an open PO (full replace of vendor/expected/lines). 404 if missing for the location, **409 `po_not_editable`** when the PO is `received` (immutable) or `cancelled` (terminal). Logs an `edited` activity entry. Non-GET write-auth gate; `who` server-derived (crew actor) else the BFF-supplied operator name.
- `POST /api/inventory/pos/:id/cancel` — optional body `{ who? }`; cancel an open PO (idempotent). 404 if missing, **409 `po_not_editable`** if already `received`. Cancelled POs are **excluded from the `GET /api/inventory` dataset** (the cancellation lives in the activity feed), so floor surfaces never see one.
- `POST /api/inventory/items/:id/toggle-86` — flips item availability. Emits an operator notification to notifications-api's ingest endpoint on **both** transitions (Phase 5 producer): a flip **to** 86 is a `warn` ("X 86'd"), a flip **back to available** is an `info` ("X back in stock") that closes the loop on the 86 alert. **Best-effort + fire-and-forget** (a notify failure is logged, never blocks the toggle), and a **no-op until** `INTERNAL_NOTIFICATIONS_API_URL` + `NOTIFICATIONS_INTERNAL_TOKEN` are set (`lib/notifications-client.ts`). Only notifications-api writes db-notifications (Iron Law 1), so this is an HTTP call, not a DB write.
- `PUT  /api/inventory/items/:id` — body `InventoryItemSave`; catalog item editor (S3), the API re-derives `cost_cents`. Also accepts `category` (floor "edit item" can re-file an item). Non-GET, so the write-auth gate applies; a catalog edit is not a stock movement, so no per-actor `who`.
- `GET  /api/inventory/items/:id/image` — raw item photo bytes (open read like the dataset; 404 when none). The browser renders it via an `<img>`; the dataset only carries the `has_image` flag, never the bytes.
- `PUT  /api/inventory/items/:id/image` — body `InventoryItemImageUpload` (base64-encoded, resized client-side); decodes + stores the bytes in Postgres (`inventory_item_images`). Route-level `bodyLimit` raised for the larger payload. Non-GET write-auth gate; no per-actor `who`.
- `DELETE /api/inventory/items/:id/image` — remove an item photo (idempotent).
- `POST /api/inventory/items/:id/packs` — body `InventoryItemPackSave`; create a packaging conversion ([ADR-0737](../../docs/decisions/0737-inventory-unit-model-stable-base-unit-per-vendor-packs-and-barcode-mapping.md)). Returns the fresh `{ item }` (with `packs`/`barcodes`). 409 `pack_exists` on a duplicate (vendor, label); marking `is_purchase_default` clears it on the item's other packs. Non-GET write-auth gate.
- `PUT /api/inventory/items/:id/packs/:packId` — body `InventoryItemPackSave`; edit a pack. 404 `pack_not_found` when the pack isn't on this item; 409 on a label clash.
- `DELETE /api/inventory/items/:id/packs/:packId` — delete a pack (idempotent); barcodes that pointed at it are re-parented to item-level (`pack_id` null).
- `POST /api/inventory/items/:id/barcodes` — body `InventoryBarcodeSave`; map a UPC/GTIN or printed code to the item (+ optional pack), upsert by `code`. 400 `unknown_pack` when `pack_id` isn't on this item. On a successful map **to a pack-less item** it emits a `info` **"finish setup" nudge** to notifications-api (barcode-onboarding P5 producer): best-effort + fire-and-forget, opt-in like the 86 / low-stock emits, `dedupeKey=inv:nopack:<itemId>` so re-scanning the same item never spams. There is no producer-side "resolve", so adding the pack later doesn't auto-clear it — the operator dismisses it once setup is done.
- `POST /api/inventory/items/:id/barcodes/mint` — body `InventoryBarcodeMintRequest` (`{ pack_id? }`); server-mint a `YR-#####` Code128 house code for a no-UPC item and register it as an `internal` barcode (barcode-onboarding D4). Idempotent per (item, pack). Fires the same pack-less **"finish setup" nudge** as the barcode map above. Write-auth gated by the global non-GET preHandler.
- `DELETE /api/inventory/items/:id/barcodes/:code` — remove a barcode mapping (idempotent).
- `GET  /api/inventory/barcode/:code` — `InventoryBarcodeResolve` (`{ item, pack }`); resolve a scanned code for the receive/count scan flow. Open read like the dataset; 404 when unknown.
- `POST /api/inventory/counts` — body `InventoryCountSubmission`. Like waste, it emits a **low-stock** notification for each item a recount takes below its minimum par (`crossedBelowPar`, one per item — a count covers many); best-effort + fire-and-forget, opt-in. The crossings are an internal signal, **not** in the API response.
- `POST /api/inventory/waste` — body `InventoryWasteSubmission`. When the waste takes an item from at-or-above its minimum par to below it (a one-shot downward crossing, `crossedBelowPar` — not on every subsequent drop), it also emits a **low-stock** operator notification (Phase 5c producer): best-effort + fire-and-forget, opt-in like the 86 emit. The crossing is computed server-side and is an internal signal — it is **not** added to the API response.
- `POST /api/inventory/pos/:id/receive` — body `InventoryReceiveSubmission`
- `GET  /api/inventory/recipes/:id` — `InventoryRecipeDetail`; recipe-editor read (open read, like the dataset).
- `PUT  /api/inventory/recipes/:id` — body `InventoryRecipeSave`; recipe editor save, full BOM + modifier replace ([ADR-0028](../../docs/decisions/0028-sales-driven-inventory-depletion.md)). Non-GET write-auth gate; no per-actor `who`.
- `POST /api/inventory/sync-sales` — manual "Sync sales" depletion trigger pulling analytics-api's read-only sold-items feed; idempotent per Clover line item, returns `InventoryDepletionRunResult`. 503 when `INTERNAL_ANALYTICS_API_URL` / `ANALYTICS_ADMIN_TOKEN` / `CLOVER_MERCHANT_ID` are unset ([ADR-0028](../../docs/decisions/0028-sales-driven-inventory-depletion.md) / S4b). Like waste/counts, it emits a **low-stock** notification for each item the depletion takes below its minimum par (`crossedBelowPar`, one-shot, deduped per item across the batch) — Phase 5c producer, best-effort + fire-and-forget + opt-in. The depletion alert is **system-driven**, so it carries no operator `who` ("…after sales depletion"). The crossings are an internal signal, **not** in the `InventoryDepletionRunResult` response.
- `GET  /api/inventory/security-settings` — `InventorySecuritySettings` (crew login IP allowlist). Open read like the dataset; reachable only internally (inventory-api is internal-only) — crew-web polls it to enforce the allowlist at the edge.
- `GET  /api/admin/crew/security` / `PUT /api/admin/crew/security` — body `InventorySecuritySettingsSave`; manager-only (bearer) read/write of the crew IP allowlist, edited from Backoffice. Stored here; **enforced in crew-web** (the only tier that sees the cook's real IP now that this API is internal-only).
- `POST /api/crew/login` — body `{ pin }`; returns `{ token, employee }` for the floor app. Rate-limited per device/IP (per-(IP,prefix) bucket + a per-IP cap), with a global brute-force-rate alarm.
- `POST /api/crew/logout`, `GET /api/crew/me`
- `GET  /api/admin/crew` — `InventoryEmployeeListResponse` (manager crew roster)
- `POST /api/admin/crew` — body `InventoryEmployeeCreateRequest`; 409 on PIN clash
- `PATCH /api/admin/crew/:id` — body `InventoryEmployeeUpdateRequest` (edit / disable via `active`)
- `POST /api/admin/crew/:id/pin` — body `InventoryEmployeePinResetRequest`; 409 on PIN clash
- `GET  /api/health`, `GET /api/ready`

## Rules

- All app-facing DTOs (reads and write request bodies) come from `packages/contracts`. Never hand-write inventory DTOs here.
- Mutations run in a Prisma transaction and recompute `on_hand`. Keep `on_hand` and `flagged_86` authoritative; item *status* (ok/low/critical/over/86) stays a client-derived value.
- COGS / net-sales / `sold_today` are sales aggregates owned by `apps/analytics-api` (Iron Law 5). The values served today come from the `InventoryMetrics` placeholder row; wire them to analytics-api rather than treating this service as their source.
- Inventory writes are dual-auth: a valid crew session cookie (floor app) **or** the internal bearer token (`INVENTORY_INTERNAL_TOKEN`, trusted backoffice BFF). The crew session is checked first. In production a write with neither is refused; if no bearer token is configured, the bearer path fails closed.
- A crew session is re-validated against the DB on every write (`resolveActor`), so a disabled or removed employee is rejected immediately even while their stateless token is unexpired — disabling locks them out at once, not on next refresh.
- Manager crew admin lives under `/api/admin/*` and is **bearer-only** (a crew session never reaches it), so a logged-in cook cannot manage employees. Disable is soft (`active=false`) to preserve who-attribution history.
- The actor (`who`) recorded on a write is derived **server-side** from the crew session and overrides any `who` in the request body. Only the trusted bearer path may supply `who` via the body. Never trust a client-supplied actor on the crew path.
- Crew auth secrets (`CREW_SESSION_SECRET`, `CREW_PIN_PEPPER`) are required in production and must match what seeded the `pin_lookup` index. The crew session HMAC + PIN helpers come from `@rop/auth/crew`; do not reimplement them here. Per ADR-0020 these (along with `INVENTORY_INTERNAL_TOKEN`) are Layer-1 secrets populated from Infisical in production (dev defaults in development) and are never hand-set in `.env`.
- **Logout is best-effort.** The crew session is a stateless HMAC token with no server-side denylist, so `POST /api/crew/logout` only *clears the cookie* the browser holds — a copied token stays cryptographically valid until its 12h TTL. True revocation is `active=false` on the employee, which `resolveActor` enforces on every write (a disabled employee's still-unexpired token is rejected at once).
- **The crew-login rate limiter is in-memory and bounded.** `RateLimiter` (`lib/crew-auth.ts`) caps at `MAX_BUCKETS` (10,000) distinct `(IP, PIN-prefix)` buckets, opportunistically sweeping expired entries on each `recordFailure` and evicting the oldest when full, so a sustained probe can't grow it unboundedly. It is single-process only; when this service moves to multi-process the limiter must move to Redis (TTL-based eviction), at which point the in-memory cap goes away.
- **Errors are redacted in production.** `lib/error-handler.ts` installs `setErrorHandler` + `setNotFoundHandler`: it logs the full error server-side and returns only a generic message + `request_id` (also surfaced as an `x-request-id` header) in production, maps Prisma `P2003`→400 / `P2025`→404 to generic bodies, and never echoes the requested path on a 404. Don't bypass it by `reply.send`-ing raw exception text.
- Structured logging only; never log secrets, PINs, session tokens, or customer data.
