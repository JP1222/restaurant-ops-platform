# ADR-0034: Dead-letter queue and replay for Clover sync failures

- **Status**: Proposed
- **Date**: 2026-06-03
- **Deciders**: @example-org
- **Builds on**: [ADR-0002](0002-five-iron-laws.md) (Iron Laws 1 + 2 — DB boundary, contract boundary), [ADR-0027](0027-clover-online-payment-and-order-bridge.md) (the Clover order/sync bridge whose failures land here), [ADR-0030](0030-semantic-metric-registry-as-ai-grounding.md) (the metric-registry surface a DLQ-depth metric should eventually register against), [ADR-0014-sentry](0014-sentry-saas-over-glitchtip.md) (Sentry is the existing error sink the DLQ alert complements).
- **Resolves**: audit issue #124 (`kds-api: persist Clover sync failures in dead-letter queue with replay API`). Sibling reliability issues #119 (webhook HMAC) and #151 (analytics DTOs → contracts) are touched only where they intersect; each keeps its own ADR/PR.

## Context

A Clover order that fails to sync today can sit invisible for hours. The failure path is real but **half-built**, and the missing half is operator recovery.

**What exists.** Sync runs through BullMQ. `defaultJobOptions()` in `apps/kds-api/src/lib/queue/bullmq-client.ts:47-57` sets `attempts: 5`, exponential backoff, and — the issue's headline — `removeOnFail: 5000`. The worker (`apps/kds-api/src/worker.ts:76-79`) attaches a `failed` listener that calls `writeDeadLetterForFailedJob`, which (in `apps/kds-api/src/lib/queue/handlers.ts:172-190`) **only persists once the job has exhausted all attempts** (`job.attemptsMade < (job.opts.attempts ?? 1)` → return) into the `DeadLetterJob` Prisma model (`packages/db-kds/prisma/schema.prisma:448-461`: `merchantId?`, `jobType`, `reason`, `payload Json`, `attempts`, `createdAt`, `resolvedAt?`). Four code paths write that table: the worker terminal-failure listener, the fulfillment-enqueue catch (`apps/kds-api/src/lib/sync-order.ts:192-204`), the loyalty-enqueue catch (`sync-order.ts:253-266`), and the reconciliation catch (`apps/kds-api/src/jobs/reconciliation.ts:44-52`). It is **surfaced read-only**: `serializeOverview` carries a `deadLetterCount` (`apps/kds-api/src/routes/clover.ts:269-292`, `apps/kds-api/src/lib/ticket-serializer.ts:141-150`), `buildAdminSystemStatus` aggregates `deadLettersByType` + `recentDeadLetter` and lets a non-zero count tip overall health to `degraded`/`attention` (`apps/kds-api/src/lib/system-status.ts:113-228`), and a `kds_dlq_size` gauge already exists (`apps/kds-api/src/lib/metrics.ts:90-94`) and is refreshed on every scrape of `/api/internal/metrics` (`apps/kds-api/src/routes/metrics.ts:6-25`), which Prometheus already scrapes at `kds-api:4000/api/internal/metrics` (`observability/prometheus/prometheus.yml:21-28`).

**What is missing — the gap #124 names.**

1. **No replay.** Once a job is in `dead_letter_jobs`, nothing re-drives it. `resolvedAt` is written but never set; `clearMerchantOrderData` / nightly-reset don't touch it. Recovery today is a hand-written SQL spelunk plus a manual re-trigger — there is no documented procedure and no API.
2. **No durable BullMQ record beyond the DB row.** `removeOnFail: 5000` discards BullMQ's own failed-job copy past 5 000 entries — but because terminal failures are already mirrored into Postgres at the moment of exhaustion, the **DB row is the durable artifact**; the BullMQ failed-set is a redundant, capped convenience. The issue frames `removeOnFail` as the data-loss bug, but the row in `dead_letter_jobs` is what actually survives. This reframing matters for the decision.
3. **No alert.** A gauge that nobody alerts on is a dashboard nobody is looking at during service. Prometheus scrapes the gauge but has **no `rule_files` and no Alertmanager** wired (`observability/prometheus/prometheus.yml` has `scrape_configs` only; `observability/` contains promtail + grafana provisioning but no alert rules). So "alert when DLQ depth > 10 for >5min" is net-new alerting infrastructure, not a metric tweak.
4. **No metric dimensionality the AC asks for.** `kds_dlq_size` is labelled `job_type` only. The AC asks for `kds_dead_letter_queue_depth` **per merchant + job type**.

Why it matters: a stuck order is an order the kitchen never sees and the customer paid for. The board self-reports `degraded`, but degradation with no recovery tool means the only lever is a full reconciliation sweep or an engineer. This is correctly tagged **P0 / reliability**: silent, money-adjacent, and currently un-actionable.

**Adjacent reliability work (scope fences, not part of this ADR's decision):**

- **#119 (webhook HMAC).** The Clover webhook handler (`apps/kds-api/src/routes/clover.ts:124-247`) authenticates **only** by the optional `CLOVER_WEBHOOK_AUTH_CODE` shared-secret header (`x-clover-auth` / `x-clover-auth-code`, lines 143-148) plus a merchant allow-list (lines 171-186); there is no payload signature check. A prior HMAC-SHA256 attempt **was merged and then fully reverted** (commit `248c5fa`, reverting `4a47703`) because Clover's public docs only document `X-Clover-Auth` and the assumed `x-clover-request-hmac-sha256` header could not be confirmed — shipping a strict 401-on-missing-signature verifier risked bricking live deliveries. Note also that the handler already writes `lastSignedWebhookAt` (`apps/kds-api/src/lib/provider-app-state.ts:37-38`, `schema.prisma:86`) — a **misnomer today**, since nothing is signature-verified. #119 stays its own issue; it only borders this ADR in that an unsigned-webhook-triggered bad sync is exactly the kind of failure that should land in the DLQ rather than silently corrupt state.
- **#151 (analytics DTOs → contracts).** This is an Iron Law #2 cleanup ([ADR-0002](0002-five-iron-laws.md)): `apps/backoffice-web/lib/analytics-api/types.ts` (241 LOC, 27 hand-rolled `export interface`s) must move to zod in `packages/contracts`, following the **just-merged precedent PR #400** (#207/#200, merged 2026-06-03 02:43Z) which added `packages/contracts/src/ai.ts` + `insights.ts` and made the BFF `safeParse` the wire. It is included here **only** because the DLQ replay/list API this ADR introduces is itself a new cross-app DTO and so must be born in `packages/contracts` from day one — i.e. this ADR must not re-commit the very sin #151 exists to fix. **Critical coordination fact:** an analytics feature branch is in flight in worktree `zealous-kowalevski-daface` (`claude/costs-page`, no PR open yet) that **actively edits the exact #151 target files** — `apps/backoffice-web/lib/analytics-api/types.ts`, `apps/backoffice-web/lib/analytics-api/client.ts`, and `apps/analytics-api/src/http/dashboard.ts`. Any #151 work must land **after** that branch merges, or it will collide; this ADR does not assume a clean analytics tree.

## Decision

**Promote the existing `DeadLetterJob` table into a first-class, operable DLQ. Do not stand up a second BullMQ `kds-dlq` queue — the Postgres row is already the durable artifact; what's missing is an operator surface, an alert, and a runbook.** Concretely, six changes, all inside `apps/kds-api` + `packages/contracts` (no Iron Law crossing):

1. **Stop discarding the BullMQ failed-set silently; keep the DB as the source of truth.** Leave `attempts: 5` + backoff as-is. The DB mirror in `writeDeadLetterForFailedJob` already captures every terminal failure, so `removeOnFail` is a tuning knob, not a correctness bug — but raise it to a time-based bound (`removeOnFail: { age: 7 * 24 * 3600 }`) in `bullmq-client.ts:47-57` so a recent failed job is still inspectable in BullMQ for debugging, decoupled from the 5 000-count cliff. The **authoritative** DLQ remains `dead_letter_jobs`.

2. **Replay-capable payloads.** Today the worker DLQ row stores `{ queue, jobId, data }` (`handlers.ts:181-186`) — enough to reconstruct a `SyncOrderJob` and re-`addSync`. The three enqueue-failure writers (`sync-order.ts`, `reconciliation.ts`) store narrower payloads. Standardize every writer to persist the **minimum re-enqueue envelope** for its `jobType` (queue name + the typed job `data`, PII-free — the loyalty writer's existing comment at `sync-order.ts:258-259` already establishes "no phone in the payload"). Replay then maps `jobType` → the right enqueue call (`queue.addSync` / `enqueueFulfillment` / `enqueueLoyaltyAccrual` / re-run reconciliation window).

3. **Auth-gated admin list + replay API, contract-first.** Add to `packages/contracts` a new `packages/contracts/src/dlq.ts` (re-exported from `index.ts`) with zod: `DeadLetterJobSchema`, `DeadLetterListResponseSchema` (paged, filterable by `merchantId` + `jobType` + `resolved`), `DeadLetterReplayRequestSchema` (`{ ids: string[] }` or `{ filter }`), `DeadLetterReplayResponseSchema` (`{ requeued, skipped, failed }`). Add routes in `apps/kds-api/src/routes/admin.ts` (where the existing admin surface + the `createAdminBearerGuard` constant-time bearer guard at `apps/kds-api/src/lib/admin-bearer-auth.ts:4-23` already live) — or a dedicated `routes/dlq.ts` registered behind the same guard:
   - `GET /api/admin/dlq` → validated `DeadLetterListResponse` (reads `dead_letter_jobs`, default `resolvedAt: null`).
   - `POST /api/admin/dlq/replay` → for each selected row, re-enqueue via the normal pipeline by `jobType`, then set `resolvedAt = now()` on success. **Replay is idempotent by construction**: sync jobs already key on `syncJobId` (`bullmq-client.ts:59-67`) and the consumer's provider-event/`UNIQUE` guards dedupe, so a double-replay cannot double-create a ticket. Return per-row outcome.
   Auth: reuse the existing admin bearer guard (operator/ops token), matching how internal admin mutations are already gated; no new auth mechanism (Iron Law #3 untouched).

4. **Metric the AC asks for, on the existing scrape.** Add `kds_dead_letter_queue_depth` (gauge, labels `merchant_id` + `job_type`) in `metrics.ts` alongside the current `kds_dlq_size`, and populate it in the **same** `/api/internal/metrics` refresh loop (`routes/metrics.ts:9-21`) by widening the existing `groupBy(["jobType"])` to `groupBy(["merchantId","jobType"])`. Keep `kds_dlq_size` as a deprecated alias for one release so existing Grafana panels don't break.

5. **A real alert rule + Alertmanager route.** Add `observability/prometheus/rules/dlq.yml`, wire it via a new `rule_files:` block in `observability/prometheus/prometheus.yml`, and add a minimal Alertmanager service to `docker-compose.observability.yml` routing to the existing notification path (Slack — `slack-notify.yml` exists — and/or Sentry, [ADR-0014-sentry](0014-sentry-saas-over-glitchtip.md)). Rule: `sum(kds_dead_letter_queue_depth) > 10 for: 5m`. This is the net-new infra the AC's "alert when DLQ depth > 10 for >5min" actually requires.

6. **Runbook.** Add a "DLQ recovery" section to the **existing** `docs/runbooks/clover-sync.md` (the Clover-sync runbook already lives there): how to read `GET /api/admin/dlq`, how to interpret `jobType`/`reason`, when to replay vs. when a replay will just re-fail (e.g. a permanently-deleted Clover order), and how `resolvedAt` is set. Cross-link from `apps/kds-api/AGENTS.md`.

This is deliberately the **smaller, table-centric** design: it reuses the model, the gauge, the scrape, the admin auth guard, and the runbook file that already exist, and adds the three things genuinely absent — replay, real alerting, and per-merchant labelling.

## Consequences

- **New operator capability, low new surface.** One contract file, one set of admin routes behind the existing bearer guard, one widened metric, one alert rule + a small Alertmanager addition, one runbook section. No new queue, no new table, no migration to `dead_letter_jobs` if the current columns suffice (they do for `SyncOrderJob` replay; a follow-up `replayedAt`/`replayCount` column is optional polish, deferred).
- **`removeOnFail` reframed, not just bumped.** The fix isn't "raise 5000" — it's "the DB row is canonical, BullMQ's failed-set is debug convenience." Worth stating in the PR so a future reader doesn't re-introduce a count-based cliff thinking it's the bug.
- **Replay safety leans on existing idempotency.** Because re-enqueue reuses `syncJobId` + the provider-event uniqueness guards, replay is safe to spam. The one sharp edge: replaying a job whose root cause is permanent (deleted order, malformed historical payload) will re-fail and re-dead-letter — the runbook must tell the operator to `resolve`-without-replay those, so the DLQ doesn't thrash. A `resolvedAt`-without-replay ("acknowledge / give up") action on the endpoint covers this.
- **Alerting is now a thing this repo does.** Standing up the first `rule_files` + Alertmanager is a small but real ops commitment (a container, a route, a Slack/Sentry target). Once it exists, future alerts (queue depth, webhook staleness) are cheap. This is a feature, but it's load the owner takes on.
- **Metric rename ripple.** Adding `kds_dead_letter_queue_depth` while keeping `kds_dlq_size` aliased means one release of two gauges for the same thing; Grafana panels migrate on the owner's schedule, then the alias drops.
- **Coordination cost with in-flight work.** The DLQ contract addition (`packages/contracts/src/dlq.ts`) is **independent** of the analytics DTO files, so it can land immediately without waiting on the `costs-page` branch. The **#151** analytics migration, if folded into the same wave, must sequence **after** `claude/costs-page` merges (it edits the same `types.ts`/`client.ts`/`dashboard.ts`) — so this ADR recommends shipping #124 first/standalone and treating #151 as a separately-sequenced follow-up, not a co-PR.
- **Cost is bounded.** Issue estimate is M (<300 LOC across queue config + worker + admin route); the contract + alert + runbook push it slightly but it stays a single reviewable PR (or a 2-PR split: API/contract, then observability/runbook).

## Alternatives considered

- **Stand up a dedicated second BullMQ queue `kds-dlq` (the literal AC reading).** Genuine option: terminally-failed jobs get `add()`-ed to a real Redis-backed `kds-dlq`, and replay is "move job from `kds-dlq` back to `kds-sync-hi`." Honest upside: it's BullMQ-idiomatic and replay is a queue op, not a DB read + re-enqueue. Downside, and why it's not recommended: it **duplicates** the durable record we already write to Postgres — we'd have the same failure in `dead_letter_jobs` *and* in a Redis queue, and they can drift (Redis is volatile; the DB row survives a Redis flush). The existing health/overview/metric surfaces all read the **table**, so a second source of truth means rewiring `system-status.ts`, `serializeOverview`, and the metrics route to reconcile two stores. The table-as-DLQ keeps one source of truth and reuses every read surface already built. (If the owner prefers the queue-native model, the cleanest variant is *replace* the DB write with the queue, not run both — but that loses the survives-Redis-flush durability that made the DB mirror valuable in the first place.)
- **Reduce attempts / add manual retry only, skip alerting + metric work.** Smallest possible change: just add `POST /api/admin/dlq/replay` and call it done. Rejected as under-delivering the P0: without the per-merchant metric and the >10-for-5min alert, the failure stays invisible until someone happens to look at the Operations page — which is exactly today's problem. The AC explicitly lists the metric, the alert, and the runbook; replay alone is half a fix.
- **Auto-replay with capped backoff (self-healing DLQ).** Tempting: a scheduler job that periodically re-drives unresolved `dead_letter_jobs` N times before giving up. Rejected as the *primary* mechanism because the failures that reach the DLQ have **already** exhausted 5 attempts with exponential backoff — blind auto-replay mostly re-fails and burns Clover rate-limit budget (`kds_clover_rate_limit_wait_seconds` exists for a reason), and risks masking a systemic outage as a slow trickle of retries. Operator-gated replay (with the option to add a *bounded, opt-in* auto-replay for a known-transient `jobType` like enqueue-failures later) is the safer default. Worth revisiting once we can classify `reason` into transient vs. permanent.
- **Push everything to Sentry and skip the in-app DLQ API.** We already have Sentry ([ADR-0014-sentry](0014-sentry-saas-over-glitchtip.md)); terminal failures could just be Sentry events with a "replay" runbook that re-triggers via the existing reconciliation path. Rejected: Sentry is the right place to *notice* and *triage*, but it can't *replay* a specific stuck order, and reconciliation is a blunt full-window sweep, not a targeted re-drive. The DLQ API gives per-order recovery Sentry can't. (Sentry stays the alert sink option in change #5 — complementary, not a substitute.)

## Open questions (owner / ops to resolve)

These gate ratification but not the design shape:

1. **Replay window / retention.** How long do unresolved `dead_letter_jobs` stay replayable before they're archived/pruned — 7 days, 30, indefinite? And is a stuck order older than, say, a few hours even worth auto-surfacing for replay, or should stale ones require explicit operator intent? (Drives whether we add a retention sweep + a `staleAfter` concept.)
2. **Alert destination + who's on call.** Slack (the existing `slack-notify.yml` path), Sentry, both? And is "DLQ > 10 for 5min" the right threshold for a single-merchant box, or too chatty / too quiet given real order volume? (Drives the Alertmanager route + the rule constants.)
3. **#119 prerequisite, unchanged from the revert.** Does the Clover Developer Dashboard for this app actually expose a webhook **signing secret** / HMAC field, and which header carries the digest? Until that's confirmed in the dashboard, #119 stays deferred. If it *is* confirmed, where should the secret live — Infisical (like `CLOVER_WEBHOOK_AUTH_CODE` today, per [ADR-0020](0020-adopt-infisical-for-runtime-secrets.md)) or `AppSetting category=secret` ([ADR-0016](0016-app-setting-table.md))? This ADR doesn't decide #119; it only notes that an unsigned-webhook-induced bad sync is the kind of failure the DLQ now lets you recover from.
4. **#151 sequencing.** Confirm the intended order: land #124 (this ADR) standalone, let `claude/costs-page` merge, *then* do the analytics-DTO → contracts migration (#151) as its own wave following the PR #400 pattern — rather than bundling #151 into the DLQ PR. (Recommended, but the owner owns the wave plan.)
5. **Replay actor / audit.** Should each replay write an audit row (who replayed which DLQ entry, when) for the money-adjacent paths, or is the bearer-guarded endpoint + `resolvedAt` timestamp sufficient?
