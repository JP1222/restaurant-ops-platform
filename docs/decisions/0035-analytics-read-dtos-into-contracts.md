# ADR-0035: Move analytics-api read DTOs into @rop/contracts

- **Status**: Proposed
- **Date**: 2026-06-03
- **Deciders**: @example-org
- **Builds on**: [ADR-0002](0002-five-iron-laws.md) (Iron Law 2 — the cross-app DTO source must be `packages/contracts`), [ADR-0012](0012-architecture-as-guardrails.md) (boundaries as build-failing guardrails), [ADR-0030](0030-semantic-metric-registry-as-ai-grounding.md) and [ADR-0031](0031-profitability-analytics-cost-dimension.md) (the in-flight analytics work this change must sequence around). Follows the pattern set by PR #400 (audit #207 / #200), which moved two backoffice DTOs into contracts as zod.

## Context

Every shape `apps/analytics-api` returns and `apps/backoffice-web` consumes is hand-typed in `apps/backoffice-web/lib/analytics-api/types.ts` — 219 LOC, 20+ `export interface`s (`SalesResponse`, `HourlyResponse`, `TopItemRow`/`ItemsResponse`, `ItemHourlyResponse`, `ItemModifiersResponse`, `OpsOverviewResponse`, `OpsJobsResponse`, `OpsWebhookVerificationsResponse`, `DatabaseResponse`, and their row sub-shapes). These cross an app boundary (analytics-api → backoffice-web BFF → browser) and so, under **Iron Law 2** ([ADR-0002](0002-five-iron-laws.md):26 — "Cross-app DTOs flow through `packages/contracts` (Zod). No hand-written DTOs at app boundaries."), the source must live in `packages/contracts`. ADR-0002 even names this exact case in its evidence ("A Backoffice analytics page that hand-rolled a JSON shape for the trends chart → moved into `packages/contracts`").

Two concrete problems make this more than a hygiene item:

1. **No validation runs on the wire.** `apps/backoffice-web/lib/analytics-api/client.ts:69` returns `res.json() as Promise<T>` — an unchecked cast. analytics-api's `src/http/dashboard.ts` (954 LOC) uses no validation library at all. Analytics rows come straight from Postgres aggregate SQL, where every numeric is typed `number | string` in `types.ts` precisely because pg returns `numeric`/`bigint` as a **string**. A stray `null`, a numeric overflow, or a renamed column becomes a runtime UI crash with no boundary to catch it, on a manager-facing dashboard.

2. **Active duplication already exists.** `TopItemRow`/`ItemsResponse`/`ItemHourlyResponse`/`ItemModifiersResponse` in `types.ts` are byte-for-byte the same shapes as `MenuItemRowSchema`/`MenuItemsResponseSchema`/`MenuItemHourlyResponseSchema`/`MenuItemModifierRowSchema`, which **already live in `packages/contracts/src/index.ts:643-710`** (added for the Phase 6 menu-engineering page). Neither references the other. We are maintaining the same contract twice, in two type systems, and they can silently diverge.

There is also a **naming hazard**: `packages/contracts/src/ops.ts` already exists, but it is the **CI/CD / Operations-page** surface (runners, deploy dispatch, build freshness) — *not* analytics OLAP ops. The analytics `Ops*` DTOs (`OpsOverviewResponse`, `OpsHealthSummary`, sync jobs, webhook verifications, mart table stats) are a different domain and must not be merged into that file.

**This is not a clean tree.** The analytics surface is the single most contended area of the repo right now: branches `claude/cost-metrics`, `claude/phase1-dim-item-cost`, `claude/phase1-plate-cost`, `claude/costs-endpoint`, `claude/costs-page` (the last with a live worktree) are all in flight, implementing the [ADR-0031](0031-profitability-analytics-cost-dimension.md) cost dimension and [ADR-0030](0030-semantic-metric-registry-as-ai-grounding.md) metric registry. ADR-0031 explicitly adds a contribution-margin measure to the menu-engineering shapes and nulls out items with no plate cost — i.e. it **mutates the very `ItemsResponse`/`MenuItemRow` shape** this ADR wants to freeze into contracts. Any plan that ignores this will collide. `types.ts` is consumed by ~15 backoffice files (hooks, transforms, ops components), so the refactor is wide even though it is shallow.

This is a sibling to the other two open P0 audit items on the same reliability sweep — [#119](https://github.com/example-org/restaurant-ops-platform/issues/119) (verify Clover webhook HMAC on every payload) and [#124](https://github.com/example-org/restaurant-ops-platform/issues/124) (persist Clover sync failures in a dead-letter queue with a replay API). All three are "the boundary trusts data it should validate / the failure path is invisible." #151 is the cheapest and lowest-risk of the three (pure TypeScript/zod, no DB migration, no prod-secret dependency), so it is the natural first cut; the other two are scoped separately and noted under Alternatives so the owner can sequence the whole P0 batch coherently.

## Decision

**Add a dedicated `packages/contracts/src/analytics.ts` of zod schemas for the analytics read surface, validate every analytics response at the backoffice BFF before it leaves `client.ts`, delete the `TopItemRow` duplicate in favor of the existing `MenuItemRow`, and ship it as a per-shape multi-PR sequence that *rebases onto* the in-flight cost-dimension work instead of racing it.** Follow PR #400 (#207/#200) move-for-move: new contracts file → `safeParse`/`parse` at the BFF → delete the local duplicate → tests in the contracts package.

1. **New `packages/contracts/src/analytics.ts`**, re-exported from the barrel (`src/index.ts` already does `export * from "./ops.js"` etc.; add `export * from "./analytics.js"`). It exports zod schemas for at minimum the AC set — `SalesResponseSchema`, `HourlyResponseSchema`, `ItemsResponseSchema`, `OpsOverviewResponseSchema`, `DatabaseResponseSchema` — plus the remaining wire shapes (`ItemHourlyResponse`, `ItemModifiersResponse`, `OpsJobsResponse`, `OpsWebhookVerificationsResponse`) and their row sub-schemas. Reuse the existing `numericFromPg = z.union([z.number(), z.string()])` helper (already defined at `index.ts:643`) for every pg-numeric column so the "string-from-Postgres" reality is encoded once, named, and tested — instead of re-spelled as `number | string` in 40 places.

2. **Delete the duplicate, do not re-add it.** `ItemsResponseSchema` is built on the **existing** `MenuItemRowSchema` (`index.ts:645`), not a new copy. The `TopItemRow` interface in `types.ts` is deleted and its consumers re-import `MenuItemRow` from `@rop/contracts`. Same for `ItemHourly`/`ItemModifier`, which fold into the existing `MenuItemHourly*`/`MenuItemModifier*` schemas. This satisfies the AC's "delete the duplicate `TopItemRow` and replace with `MenuItemRow`" and resolves the divergence risk at the root.

3. **Validate at the BFF boundary.** `lib/analytics-api/client.ts` stops casting `res.json() as T` and instead `safeParse`s each response against its schema. On a miss it maps to a structured **502 `bad_gateway`** (the upstream returned a shape we don't trust) — distinct from analytics-api's own non-2xx, which already throws `AnalyticsApiError`. This is the same posture #400 took for the inbound `InsightsResponse` (`.parse` before send) adapted to a read client. Per-panel fail-open-vs-fail-closed is an open question below.

4. **Keep `analytics.ts` as the network contract; `types.ts` shrinks to UI-derived view shapes only.** The transforms under `lib/analytics-api/*-transform.ts` produce view models (`TrendsView`, `TopItemView`, daypart shapes) that are **backoffice-internal** and do not cross an app boundary — those stay in the app (renamed/relocated as needed), and `types.ts` is reduced to exactly those, or deleted if everything moves. This respects the contracts AGENTS.md rule "Add UI-only convenience fields [only] … [if] the backend contract intentionally exposes them."

5. **Do NOT touch `packages/contracts/src/ops.ts`.** The analytics OLAP ops shapes go in `analytics.ts` (or a sibling `analytics-ops.ts`); the existing `ops.ts` stays the CI/CD-page surface. No symbol named `Ops*` may collide across the two files.

6. **Sequencing is part of the decision, not an afterthought.** Because ADR-0031's cost branches mutate the menu-item shape, the **recommended** order is: (a) land the small, uncontended schemas first — `SalesResponseSchema`, `HourlyResponseSchema`, `DatabaseResponseSchema`, the `Ops*` schemas — none of which the cost work touches; (b) hold the `ItemsResponse`/`MenuItemRow` consolidation until the in-flight plate-cost branches merge (or coordinate a single combined change), so the margin columns land in the schema **once**. Each PR stays <300 LOC per the AC's "split per response shape." Every analytics PR rebases on fresh `main` before opening, per the repo's "don't start work on a stale tree" rule.

## Consequences

- **`packages/contracts` gains `analytics.ts`** (~150–200 LOC of zod) and one barrel export. The contracts test suite gains an `analytics.test.ts` exercising the nullable/`numericFromPg` edge cases — exactly the coverage #400 added for its new files. iOS `Generated/Contracts.swift` is **not** affected (no native consumer of analytics read DTOs), so the `sync-contracts.sh --check` guard stays green.
- **`apps/backoffice-web` loses ~219 LOC of hand-rolled interfaces** and gains real runtime validation on the analytics boundary. ~15 importers of `./types` re-point to `@rop/contracts` (mechanical). One behavioral change to flag in review per the repo's Review Guidelines: a malformed upstream row now yields a 502 instead of a half-rendered card — a deliberate, called-out shift from "trust and crash later" to "fail at the boundary."
- **The duplication is eliminated, not relocated.** After this, there is one source for the menu-item shape, and ADR-0031's contribution-margin field has exactly one place to land.
- **Cost: coordination, not code.** The dominant risk is merge contention with the live cost-dimension work, which is why the sequencing in Decision §6 is mandatory rather than advisory. If the owner picks the "ship #151 first" alternative below, the cost branches must rebase and add fields to a just-frozen schema — a deliberate trade of refactor-rework for unblocking a P0 sooner.
- **No DB migration, no new env, no deploy gate.** This is TypeScript/zod only. `pnpm build && pnpm lint && pnpm test && pnpm docs:check` is the full gate (no `test:integration` needed — no DB/migration path touched).
- **Sets the template for the other two P0s.** #119 and #124 are tracked under their own issues; this ADR does not implement them, but it establishes the "validate at the boundary" posture #119 extends to webhook authenticity and notes #124's replay surface as the next reliability cut.

## Alternatives considered

- **Ship #151 now against today's revenue-only shapes; let the cost branches rebase onto the new contract.** Honest trade, not a strawman: it unblocks a P0 immediately and forces all future analytics DTO work through contracts from here on. The cost: ADR-0031's branches must then *add* `plate_cost`/`contribution_margin` to a freshly-frozen `MenuItemRowSchema`, touching it twice and risking a contract churn mid-flight. Recommended only if the owner wants the P0 closed before the cost work lands. (Surfaced as the first open question.)
- **Hold #151 entirely until the cost dimension merges, then do one combined move.** The opposite trade: zero double-touch of `MenuItemRow`, the margin columns land in contracts on the first pass — but a P0 reliability item waits on feature work of uncertain timing, and the un-validated `res.json() as T` cast stays in prod that whole time. Reasonable if the cost branches are days, not weeks, out.
- **Validate in analytics-api too (it parses its own output before send), not just at the BFF on receipt.** More correct in principle — the producer owns its contract — and it would catch a bad row at the source. But `dashboard.ts` uses no validation library today; adding `@rop/contracts` as an analytics-api runtime dependency and wrapping 20+ endpoints is a far larger blast radius than the BFF-only change, against a service with multiple live branches. Defer to a follow-up; the BFF gate already closes the user-facing crash. (Surfaced as an open question.)
- **Generate the schemas from the SQL / introspect the mart instead of hand-writing zod.** Tempting given the shapes mirror `mart` columns, but there is no codegen pipeline here, the column→DTO mapping is hand-shaped (camelCase envelopes, computed `attach_rate`, nullable joins), and it would couple the contract package to analytics-api's schema. Rejected as over-engineering for ~200 LOC; the hand-written-zod-in-contracts pattern (#400) is the house norm.
- **Do nothing / leave DTOs hand-typed in the app.** Rejected: it is a standing Iron Law 2 violation on a path that already carries an active duplicate, and it leaves a manager-facing dashboard one malformed aggregate row away from a runtime crash with no boundary to catch it.
