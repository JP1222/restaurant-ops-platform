# ADR-0033: Verify Clover webhook HMAC signatures on every payload

- **Status**: Proposed
- **Date**: 2026-06-03
- **Deciders**: @example-org
- **Builds on**: [ADR-0002](0002-five-iron-laws.md) (Iron Law 2 — webhook DTOs already flow through `packages/contracts`), [ADR-0020](0020-adopt-infisical-for-runtime-secrets.md) (where a new signing secret would live), [ADR-0016](0016-app-setting-table.md) (the at-rest-encrypted secret alternative), [ADR-0027](0027-clover-online-payment-and-order-bridge.md) (the Clover order-ingress path this webhook feeds). Sibling reliability work on the same ingress pipeline: issue #124 (sync-failure dead-letter + replay, `needs-adr`) and issue #151 (analytics read DTOs → contracts) — see *Consequences → Sequencing*.

## Context

The Clover webhook endpoint is authenticated by **one shared-secret header check** and nothing else. In `apps/kds-api/src/routes/clover.ts:143-148`, `handleCloverWebhook` reads `x-clover-auth` / `x-clover-auth-code` and 401s only when `cloverWebhookAuthCode` is *set* and mismatched; when the secret is unset it accepts the body anonymously. After that single gate the handler writes straight through: `cloverWebhookEvent.createMany` (`clover.ts:197-202`), `createProviderEvents` (`:204`), and `enqueueProviderEvents` onto the BullMQ sync queue (`:222`). There is **no signature over the payload bytes** — `apps/kds-api/src/lib/clover-webhooks.ts` parses and normalizes (`parseCloverWebhookEvents`) but verifies nothing.

The risk (issue #119, labelled **P0 / security / reliability**): a leaked auth code, or a captured-and-replayed request, lets an attacker inject or replay order events that become real KDS tickets and feed downstream loyalty accrual ([ADR-0022](0022-loyalty-ledger-and-accrual.md)). The shared secret is a bearer token sent in cleartext on every delivery — exactly the property HMAC-over-body is meant to remove. (Per-event dedup via `buildCloverWebhookFingerprint` + `skipDuplicates` blunts *naive* replay of an already-seen event, but does nothing against a forged or mutated payload under a leaked code.)

This is a **second attempt**. The first (PR #258, commit `4a47703`) was reverted wholesale in `248c5fa` for two honest reasons, both still on the record in `apps/kds-api/AGENTS.md`:

1. **The header was an unverified assumption.** #119 asserts Clover sends `x-clover-request-hmac-sha256`, but Codex's P1 review found the public Clover docs only document `X-Clover-Auth`; the team could not independently confirm an HMAC header exists. Shipping a strict *401-on-missing-signature* verifier on that guess risks **bricking real deliveries** in production.
2. **At the time, no live webhook traffic.** Order sync ran token-based via Clover REST, so the verifier guarded a dead path — pure downside.

Reason (2) **has since changed**: per the ops record, App-level Clover webhooks were enabled and verified in production on 2026-06-02 (merchant `EXAMPLEMERCH1`, URL `/api/clover/webhooks`) to cut order→board latency from ~18s to ~1-3s. So the endpoint is now load-bearing in prod, which *raises* the security stakes — but reason (1) is **un-changed**: we still have not confirmed, from the dashboard, that Clover signs deliveries or which header carries the digest. The correct fix must close the security gap **without re-introducing the production-bricking failure mode**.

We are not starting from scratch. The repo already has every primitive:

- `computeHmacSha256Hex(secret, payload)` and `timingSafeCompare(left, right)` in `apps/kds-api/src/lib/crypto.ts`.
- A **working, shipped precedent**: the Deliverect webhook verifier in `apps/kds-api/src/lib/deliverect-client.ts` (header candidates `x-server-authorization-hmac-sha256` / `x-deliverect-hmac-sha256`, `sha256=`-prefix normalization, fail-closed-in-prod semantics).
- The exact reverted code is recoverable from `4a47703` (the `preParsing` raw-body capture hook + `verifyCloverWebhookSignature`), so the implementation cost is mostly *re-application plus a safer rollout*, not green-field.

## Decision

**Re-introduce HMAC-SHA256 verification of the raw Clover webhook body, gated behind a config flag that defaults to fail-OPEN ("verify-and-observe") until the signing secret + header are confirmed from the live Clover dashboard, then flip to fail-CLOSED.** This keeps the verifier in the tree, earns operational confidence from real traffic, and removes the all-or-nothing bet that forced the first revert.

Concretely:

1. **Capture the raw body, scoped to the webhook paths.** Re-apply the `4a47703` `preParsing` hook in `registerCloverRoutes` that buffers the exact request bytes onto `request.rawBody` only for `POST /api/clover/webhooks` and `/webhooks/clover`, leaving every other Clover route on the default JSON path. HMAC must be computed over the bytes Clover signed, not a re-serialized object.
2. **Add a `verifyCloverWebhookSignature(...)` in `clover-webhooks.ts`** that mirrors the Deliverect verifier: read a configurable header (default candidates `x-clover-request-hmac-sha256`, `x-clover-signature` — **treated as a hypothesis, not fact**, see Open Questions), normalize a `sha256=` prefix, compute `computeHmacSha256Hex(secret, rawBody)`, and compare with `timingSafeCompare`. Reuse the existing `crypto.ts` helpers — do not add a new crypto path.
3. **Three-state rollout flag**, not the reverted binary fail-closed:
   - **`off`** — current behavior (shared-secret only). Safe default on deploy.
   - **`observe`** (recommended initial state once a secret is configured) — compute the HMAC, emit a new metric, log mismatches, **but never reject**. This proves the header name + signing string against live Clover deliveries with zero risk of dropping a real order. This is the step that *retires the unverified-assumption objection with data instead of a guess*.
   - **`enforce`** — reject unsigned/invalid payloads with **401 before any DB write** (the acceptance-criteria target), keeping the shared-secret check as a defense-in-depth pre-filter.
   Drive it via a config field (e.g. `cloverWebhookVerifyMode`) alongside the existing `cloverWebhookAuthCode` in `apps/kds-api/src/config.ts`, plus `cloverWebhookSigningSecret` + `cloverWebhookSignatureHeader` (the fields the revert removed).
4. **New observability metric** (the repo has none for this today): a counter `kds_clover_webhook_signature_verifications_total{provider="clover",result}` where `result ∈ {valid, invalid, missing_header, skipped}`, registered in `apps/kds-api/src/lib/metrics.ts` next to `kdsWebhookAckSeconds`. In `observe` mode this is the evidence that tells the owner it is safe to flip to `enforce`; it also surfaces in the analytics ops dashboard already fed by `audit.webhook_verifications` (`apps/analytics-api/src/http/webhooks.ts`).
5. **Unit tests** for valid signature, invalid signature, missing header, and each of the three modes (the acceptance criteria), modeled on the existing Deliverect verifier tests.
6. **Document the confirmed dashboard config in `apps/kds-api/AGENTS.md`** — replacing the current "deferred — issue #119" stub with the verified header name, secret location, and the `off → observe → enforce` runbook. The AGENTS.md note is updated **only with confirmed facts**, per the lesson already written there.

The secret itself is sourced per the owner's Open-Question answer (Infisical Layer-1, symmetric to `CLOVER_WEBHOOK_AUTH_CODE` under [ADR-0020](0020-adopt-infisical-for-runtime-secrets.md) — the recommended default — **or** an encrypted per-merchant column like Deliverect's `hmacSecretCipher` under [ADR-0016](0016-app-setting-table.md) if Clover proves to be per-merchant).

## Consequences

- **Security gap closed on the now-live path** without an all-or-nothing flip. The `observe` stage means the *only* way this attempt drops a real order is if the owner advances to `enforce` before the metric says the header/secret are correct — a deliberate, reversible action, not a blind deploy. This directly answers the two revert reasons.
- **New surfaces:** a `preParsing` raw-body hook (webhook paths only), one verifier function, ~3 config fields, one Prometheus counter, an AGENTS.md section. Estimated **S–M (<200 LOC)** including tests — slightly above #119's "S (<150 LOC)" estimate because of the three-state flag + metric the original lacked. No DB migration if the secret lives in Infisical; **one migration** (a `cloverSigningSecretCipher` column) only if the owner picks per-merchant storage.
- **Rollout is staged and reversible:** deploy with `off` (no behavior change) → set the secret + `observe` → watch `result=valid` track delivery volume with zero `invalid` for a few days of real orders → flip `enforce`. Roll back to `observe`/`off` instantly via the flag if a real delivery ever 401s. The `last-built` deploy gate (user-gated) is unaffected.
- **Cost / liability:** the verifier hashes every webhook body — negligible CPU at restaurant volume. The real cost is **operational discipline**: someone must confirm the dashboard facts and watch the metric before `enforce`. If Clover turns out **not** to sign deliveries at all, the verifier simply stays in `observe`/`off` and the shared-secret check (which we never remove) remains the control — no wasted blast radius, unlike the reverted version.
- **Sequencing / coordination with sibling audit work (explicitly in-scope per the audit ticket cluster):**
  - **vs #124 (dead-letter + replay, `needs-adr`):** both touch the *same* Clover ingress pipeline but at **different stages** — #119 is *admission control at the HTTP edge* (reject bad payloads before `createProviderEvents`), #124 is *terminal-failure handling at the worker tail* (`worker.ts:76-79` → `writeDeadLetterForFailedJob`, which today writes `deadLetterJob` **once** when `removeOnFail: 5000` discards the BullMQ record — `bullmq-client.ts:54-56`). They do not conflict and can land in either order; doing #119 **first** is preferable so the DLQ that #124 builds isn't polluted with forged/replayed jobs. #124 remains its own ADR (queue-topology + alerting decision); this ADR only notes the shared pipeline.
  - **vs #151 (analytics read DTOs → contracts):** **no file overlap** with this ADR. The caution is process, not code: `apps/analytics-api` currently has a **live feature branch in flight** (`claude/analytics-metric-registry`, `claude/analytics-metric-endpoint`), so #151's contract-package move must rebase onto that branch's tree, not a clean `main`, and follow the **just-merged PR #400 pattern** (#207/#200) — add zod schemas under `packages/contracts/src/`, `safeParse` on the wire, delete the hand-rolled `lib/analytics-api/types.ts` duplicates, split per response shape to keep each PR <300 LOC. This ADR touches neither analytics-api nor contracts, so it can proceed in parallel and is called out here only so the owner sequences the analytics-side work around its own in-flight branch.

## Alternatives considered

- **Re-ship the reverted binary fail-closed verifier as-is (#258 / `4a47703`).** Rejected for the original reason, which still holds: it 401s on a *missing* signature under an **unconfirmed** header assumption, so the first malformed-or-unsigned real delivery silently drops a paying customer's order. The three-state flag is the minimal change that keeps the (now correct) security intent while removing that failure mode. Honest tradeoff: slightly more code and an operational "watch the metric, then flip" step versus shipping in one PR.
- **Keep shared-secret-only, just harden it (rotate `CLOVER_WEBHOOK_AUTH_CODE` regularly, require it set in prod).** Cheapest, zero new code, and genuinely reduces leaked-code exposure window. Rejected as the *primary* control because it is still a replayable bearer token — it cannot detect a forged or mutated body, which is the actual #119 threat. Worth doing **anyway** as defense-in-depth (and this ADR keeps the check), but it is not a substitute for payload integrity.
- **Add a replay/timestamp window instead of (or before) HMAC** — reject events whose `modifiedTime` is older than N minutes, leaning on the existing `buildCloverWebhookFingerprint` dedup. Rejected as the lead fix: it mitigates *replay* but not *forgery*, and Clover legitimately re-delivers on retry, so a tight window risks dropping valid late deliveries. Reasonable as a **later** hardening layered on top of HMAC, not as the answer to a security-labelled integrity gap.
- **Verify at the edge (Traefik / a Cloudflare Worker) before the request reaches kds-api.** Rejected: the suite's edge is the legacy Traefik + Cloudflare hybrid with no app-secret context, and pushing HMAC logic outside the app fragments the security boundary and the secret store, contradicting the in-app Deliverect precedent and ADR-0020's secret model. Keeping verification in the Fastify handler, beside the body it protects, is simpler to test and reason about.
- **Do nothing / leave it deferred.** Rejected: tenable only while there was no live traffic — the condition that justified the 2026-05-28 revert. Webhooks are now in production (2026-06-02), so the P0 security gap is live and the "no traffic, pure downside" argument no longer applies.
